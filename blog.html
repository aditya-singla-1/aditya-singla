How Speculative Decoding & KV-Cache Paging 3× LLM Inference Throughput: A First-Principles Breakdown

Auto-regressive large language models are notorious for being memory-bandwidth bound rather than compute bound. Here is how modern inference engines (vLLM, TensorRT-LLM) break through this fundamental hardware ceiling using speculative verification and virtual memory paging.

1. The Core Bottleneck: Memory Bandwidth vs Compute

When an LLM generates text, it processes tokens sequentially one by one. For every single token generated, the GPU must read all 70+ billion parameters from High-Bandwidth Memory (HBM) into SRAM cache. Because the arithmetic intensity (FLOPs per byte transferred) is minimal during single-token generation, modern GPUs spend >80% of their clock cycles simply waiting for memory transfers.

Hardware Reality Check
An NVIDIA H100 provides ~3,350 TFLOPs of FP16 tensor compute, but only 3.35 TB/s of memory bandwidth. Generating 1 token on a 70B model requires reading ~140 GB of weights. Thus, the physical throughput limit per GPU is capped purely by bus speed.

2. The System Design Solution: Speculative Decoding

Instead of executing the massive primary model (e.g. 70B) for every token, we pair it with a compact, ultra-fast Draft Model (e.g. 1B–3B parameters).

The draft model quickly guesses the next $K$ tokens (e.g. $K=5$). The primary model then verifies all $K$ candidates in a single parallel matrix multiplication forward pass. If 4 of the 5 tokens are accepted, we achieve 4 tokens of generation in the time of roughly 1 memory-read cycle of the large model.

# Speculative Verification Pipeline 1. Draft Model generates K candidate tokens: [t1, t2, t3, t4, t5] (Cheap memory access) 2. Target Model runs ONE parallel evaluation pass for all K positions. 3. Accept tokens where Target_Prob(ti) >= Draft_Prob(ti). 4. Reject remainder & emit verified prefix. Result: 2.5x - 3.2x latency reduction with mathematically identical output distribution.

3. Key Takeaway for Data & Backend Engineers

The architectural pattern here mirrors classical CPU branch prediction and distributed batching: transform sequential memory-latency bottlenecks into parallelized compute verification. When designing high-throughput backends, always ask if you can trade idle compute for eliminated I/O waits.

ClickHouse vs PostgreSQL: When to Shift from Row-Store OLTP to Columnar OLAP

Traditional relational databases collapse when executing analytical aggregations across 100M+ event streams. Here is an architectural comparison of row-oriented storage vs vectorized columnar execution, partitioning strategies, and ClickHouse MergeTree mechanics.

The Architectural Tradeoff

Row-oriented databases (PostgreSQL, MySQL) store entire records contiguously on disk. This is optimal for transactional single-row inserts and point lookups (OLTP), but reading 5 columns across 50,000,000 rows forces the OS to load every unrelated field from disk. Columnar engines (ClickHouse) store each attribute in independent compressed column chunks with SIMD vectorization, achieving 100× faster analytics.
